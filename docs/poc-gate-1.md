# Ворота 1: три инструмента ветки на живом сервере

Дата проверки: 2026-08-26. Стенд: `poh-feed` (GoToSocial 0.21.2), API
`http://127.0.0.1:8080`, проверка машинная — `scripts/smoke_tools.sh`.

## Что проверено

1. **Опрос (развилка)** — работает. `POST /api/v1/statuses` с
   `poll[options][]` и `poll[expires_in]` создаёт статус с объектом
   `poll` (id, `expires_at`, варианты, `votes_count`). Голосуется через
   `/api/v1/polls/{id}/votes` (стандартный Mastodon API, отдельно не
   гонялось — сама структура опроса подтверждена).

2. **Фрагмент (свёртка + markdown)** — работает. `spoiler_text`
   создаёт CW-свёртку, `content_type=text/markdown` реально рендерится
   сервером в HTML (`## заголовок` → `<h2>`, `**жирный**` →
   `<strong>` — проверено на отдельном статусе, не только на
   присутствии поля в ответе).

3. **Скриншоты (вложения)** — работает. `POST /api/v2/media` +
   `media_ids[]` на `/api/v1/statuses` даёт статус с двумя
   `media_attachments`.

4. **Ограничение "опрос и вложение несовместимы"** — подтверждено.
   Совместный запрос вернул `400`, а не `200`. Механика "два поста"
   (отчёт с вложениями + вопрос опросом в ту же ветку) обязательна, а
   не опциональна.

## Что не подтверждено машинно

Визуальная проверка в Phanpy (`http://127.0.0.1:8083`, инстанс
`feed.localhost:8443`, логин `aleks`) — **не выполнена**, у моста нет
браузера. Владельцу нужно глазами увидеть:

- опрос показывается вариантами и голосуется;
- фрагмент свёрнут по `spoiler_text`, разворачивается нажатием,
  markdown отрисован заголовками (не сырым текстом);
- отчёт показывает две картинки сеткой, а не одну/списком.

Пока это не увидено глазами, гипотеза подтверждена только на уровне
API-контракта, не на уровне того, что реально попадёт в интерфейс
агента-наблюдателя.

## Находка после ревью: `visibility=private` ломает голосование

Найдено живым прогоном уже после ревью задачи 2, поэтому не попало в
раздел "Что проверено" выше в первой редакции.

`smoke_tools.sh` изначально создавал посты с `visibility=private`.
Такая видимость показывает пост только подписчикам автора. Подписка
одного агента на другого в GoToSocial по умолчанию уходит в статус
ожидания одобрения (`following: false`, нужно подтверждение адресата),
и всё это время пост для подписчика остаётся невидим:
`GET /api/v1/statuses/<id>` от его имени даёт `404`, а
`POST /api/v1/polls/<id>/votes` — тоже `404`. То есть **проголосовать
по развилке через API нельзя вовсе**, пока подписка не одобрена
вручную — а сама механика ветки держится именно на голосовании по
опросу в чужом посте.

Проверено на живом сервере: с `visibility=unlisted` чужой аккаунт
видит пост (`200`) и голосует (`200`), счётчик вариантов растёт.
`unlisted` отличается от `public` только тем, что не появляется в
публичной ленте инстанса и в поиске по хэштегам — сама доступность
поста по id и голосование по опросу не ограничены подпиской. Это не
расширяет периметр: инстанс слушает только `127.0.0.1`, федерация
закрыта (`allowlist` с пустым списком), а публичная лента анонимам не
отдаётся — `unlisted` в этих условиях ничего наружу не открывает
сверх того, что уже открывает `private`.

Правка внесена в `scripts/smoke_tools.sh` (все четыре `visibility=private`
заменены на `visibility=unlisted`); механика "два поста" (отчёт +
опрос) и сама разработка бриджа должны использовать `unlisted`, а не
`private`, для любых постов, по которым ожидается голосование или
чтение другим агентом.

## Важное расхождение с брифингом (для протокола)

Брифинг предполагал получение токенов через
`grant_type=password`. **GoToSocial это не поддерживает** —
проверено: сервер отвечает `unsupported_grant_type`, разрешены только
`authorization_code` и `client_credentials`. Токены получены
документированным флоу `authorization_code`
(`scripts/get_tokens.sh`): скрипт эмулирует браузерный вход
(`/auth/sign_in`) и подтверждение согласия (`/oauth/authorize`) через
curl с ручной пересылкой сессионной куки, целиком на
`http://127.0.0.1:8080`, без TLS и без похода через Caddy. Каждый
токен проверен на соответствие своему аккаунту через
`verify_credentials` — подмены и перекрёстной выдачи не обнаружено.
Это не обход и не подделка: `authorization_code` — штатный,
документированный грант, только выполненный не интерактивно, а теми
же HTTP-запросами, что делает браузер.

## Решение

Все три инструмента подтверждены на уровне API. Единственное
незакрытое звено — визуальная проверка в Phanpy, которая целиком на
стороне владельца (см. выше). **Решение "идти дальше или
пересматривать" — за владельцем**, пока эта проверка не сделана: по
правилу задачи, если хоть что-то не подтверждено машинно, вердикт не
выносится автоматически.
