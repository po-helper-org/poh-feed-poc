# Playbook: личный Telegram как источник ленты

Как переписка из личного аккаунта Telegram попадает в ленту контура. Записано
2026-09-10 по факту сделанного, а не по замыслу.

---

## Границы: что здесь сделано, а что нет

**Сделано:** перенос уже собранных заявок из базы коллектора в ленту —
`scripts/telegram_to_feed.py`.

**НЕ сделано и в этот playbook не входит:** подключение самого Telegram.
Коллектор `dsh-communication-plugin` на этой машине **был авторизован и уже
наполнил базу до начала работы** — файл сессии `tg.session` существовал,
`inbox.db` содержал 95 заявок с отметкой времени за час до начала. Я его не
запускал и в Telegram не ходил.

Это важно не для отчётности, а для воспроизводимости: **половина цепочки
здесь не описана, потому что не выполнялась.** Что требуется для подключения
Telegram — см. раздел «Чего в этом playbook нет».

## Шаги

### 1. Учётка на каждый чат

Автором поста становится источник — как в Threads автором становится человек.
Соответствие «чат → учётка» задано словарём `ACCOUNTS` в скрипте переноса.

```bash
for u in product_radar problemhunt crm_harness tg_aleks; do
  docker exec poh-feed /gotosocial/gotosocial --config-path /gotosocial/config.yaml \
    admin account create --username "$u" --email "$u@feed.local" \
    --password "$FEED_ACCOUNT_PASSWORD"
  docker exec poh-feed /gotosocial/gotosocial --config-path /gotosocial/config.yaml \
    admin account confirm --username "$u"
done
```

### 2. Токены для учёток-источников

```bash
set -a && source .env && set +a
./scripts/get_tokens.sh product_radar problemhunt crm_harness tg_aleks
```

Скрипт принимает список учёток аргументами и **сливает** результат в `.env`,
не затирая прежние токены.

Почему не проще: **GoToSocial не поддерживает `grant_type=password` вовсе** —
отвечает `unsupported_grant_type`. Токен добывается документированным флоу
`authorization_code`, пройденным теми же запросами, что делает браузер.

### 3. Перенос

```bash
set -a && source .env && set +a
INBOX_DB=/путь/к/inbox.db python3 scripts/telegram_to_feed.py
```

Что делает:

- открывает базу коллектора **только на чтение** (`mode=ro`) и не трогает
  состояние разбора: разбор — решение человека, перенос им не является;
- склеивает подряд идущие сообщения одного автора в одном чате в пачку,
  если разрыв не больше `DELAY_BUDGET_SEC`;
- публикует пачку одним постом, ссылки выносит списком;
- дописывает исходное время отправки в текст;
- пишет журнал перенесённого **после каждой публикации**.

### 4. Подписка человека

```bash
set -a && source .env && set +a
./scripts/follow_sources.sh
```

Домашняя лента показывает только подписки. Без этого шага она пуста — и это
устройство, а не поломка, но выглядит одинаково.

Скрипт заканчивается проверкой: читает домашнюю ленту и **отказывает, если она
пуста**, называя вероятную причину.

## Решения и почему именно так

**Единица ленты — пачка, а не сообщение.** Человек говорит кусками; разрезав
высказывание на реплики, теряешь то, что он сказал целиком. Из 95 заявок
получилось 78 постов.

**Окно склейки взято из настроек коллектора,** а не выбрано. Своё число
разошлось бы с тем, которым коллектор меряет задержку.

**Исходное время — в текст поста.** Mastodon API не позволяет публиковать
задним числом. Без этой строки месячная переписка выглядела бы сегодняшней —
молчаливая ложь о времени.

**Журнал пишется после каждой публикации, а не в конце обхода.** Первая версия
писала в конце: обрыв на середине терял бы весь прогресс, и повторный запуск
задваивал ленту. Ошибка повторяет ту, что до этого ловило ревью в мосте.

**Токены не добываются самим скриптом.** Первая версия повторяла флоу входа на
Python и упиралась в 500 на шаге согласия. Вторая реализация входа разошлась бы
с рабочей — скрипт берёт токены из окружения, выдаёт их `get_tokens.sh`.

## Четыре препятствия и их причины

### Потолок частоты запросов

**Как проявлялось:** `429`, затем обрывы соединения на середине переноса.

**Причина:** у GoToSocial 300 запросов за пять минут на адрес по умолчанию.

**Решение:** `advanced-rate-limit-requests: 5000` в конфигурации. Поднят, а не
выключен: ноль снял бы и защиту от собственного цикла, ушедшего вразнос.

### Потолок памяти контейнера

**Как проявлялось:** падение и перезапуск под потоком публикаций.

**Причина:** `mem_limit: 512m` не хватало.

**Решение:** поднят до `1g`.

### SQLite поверх проброса каталога с macOS

**Как проявлялось:** `fatal error: fault`, `SIGBUS`, `split stack overflow` в
слое `database/sql`. Дважды за час, с перезапуском контейнера.

**Причина:** база лежала в проброшенном с хоста каталоге
(`./gotosocial/data:/gotosocial/storage`). SQLite с отображением файла в память
поверх проброса macOS в контейнер — известный источник ошибок шины.

**Решение:** база перенесена в том Docker, на файловую систему внутри
виртуальной машины:

```bash
docker compose stop feed
cp -a gotosocial/data gotosocial/data.backup-$(date +%H%M)
docker volume create poh_feed_data
docker run --rm -v "$PWD/gotosocial/data:/from:ro" -v poh_feed_data:/to \
  alpine sh -c 'cp -a /from/. /to/'
# в compose.yml: poh_feed_data:/gotosocial/storage
docker compose up -d feed
```

После переноса 78 постов прошли без единого перезапуска.

### Закрытые учётки-источники

**Как проявлялось:** подписки уходили в «ждёт одобрения», домашняя лента
оставалась пустой **без единого сообщения о причине**.

**Причина:** учётки создавались закрытыми и требовали ручного подтверждения.

**Решение:** снять замок и подтвердить накопившиеся запросы — токены учёток для
этого есть:

```python
call("/api/v1/accounts/update_credentials", token, {"locked": "false"}, "PATCH")
for r in call("/api/v1/follow_requests", token):
    call(f"/api/v1/follow_requests/{r['id']}/authorize", token, {})
```

## Чего в этом playbook нет

**Подключения Telegram.** Оно выполнялось до и вне этой работы. Судя по коду
плагина, требуется:

- ключ приложения на `my.telegram.org` — `TG_API_ID` и `TG_API_HASH`;
- один раз `node bin/login.mjs` — заводит файл сессии `tg.session`, дальше он
  только читается;
- область сбора: `WATCHED_FOLDERS`, `WATCHED_CHATS`, `WATCH_PRIVATE`;
- `node bin/collect.mjs` — процесс долгоживущий: сперва подписка на поток,
  потом чтение непрочитанного, дальше слушает.

Ни один из этих шагов здесь не проверялся. Прежде чем повторять их по этому
тексту — сверьтесь с README плагина.

**Обратного хода.** Лента только принимает; ответить из неё в Telegram нельзя.
В самом плагине это тоже вне первой итерации.

**Отслеживания новых сообщений.** Перенос разовый, по запуску. Непрерывной
доставки нет — при повторном запуске переносится только то, чего ещё нет.

**Разбора и классификации.** Классы заявок в плагине есть, но при переносе не
используются: посты уходят в ленту без класса. Как это могло бы выглядеть —
показано прототипом «Входящие как лента», в коде не реализовано.

**Отношения к личным данным.** Область сбора на этой машине узкая: одна папка,
личные сообщения выключены. Прежде чем расширять — учтите, что перенос копирует
содержимое во вторую базу, и удаление в Telegram её не затронет.
